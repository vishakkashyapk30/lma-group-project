# Design review, 2026-10-27

Scope: the design decisions of the project as of `main` at `bb76fbc` (plus the uncommitted `scripts/ada/serve_qwen32b.sh`) and the unmerged branch `frontend-endeavours`. Read: AGENTS.md, split.md, progress.md 0 to 0f, docs/plan.md, docs/architecture/skeleton.md, docs/evaluation-plan.md, docs/literature-to-code-map.md, docs/product-readiness.md, frontend/DESIGN.md (main and branch), the handoff notes named below, docs/report/sections/*.tex, and code in `orchestration/`, `privacy/`, `models/sarvam/policy.py`, `record/gates.py`, `rights/`, `eval/scoring/`, `eval/metrics/unsupported_fact.py`, `stores/hybrid.py`. Checks run: `pytest --collect-only` (no test run), reads of `data/stores/MANIFEST.json`, `data/eval/*` manifests, `configs/*.yaml`. No model call, no paid call, nothing committed. This note judges design, not output quality; it gives no quality score to any system output.

## Verdict

1. The engineering is unusually disciplined for a course project: typed switches with byte-identical defaults, code-stamped manifests, a scorer that refuses mixed code, spend ledgers that reserve before calling, gates checked from the event log, and a sealed blind slice.
2. The headline evaluation is not yet valid as designed: the unsupported-fact metric is scored by the same DeBERTa checker that Full uses to repair its claims, the gold labeler is the same model (`gpt-6-luna`) as the system under test, and the dense side of retrieval is a hashed n-gram embedder, not BGE-M3.
3. Breadth has outrun evidence: 61 variant ids, 42 claims and 9 test sets stand on 50 dev cases, one backend, about 2.2 USD of spend, and zero runs on the pinned tag `dev-sweep-v2`; the test-scale RQ1 run has no backend at all.
4. The privacy boundary is a name scrubber, not pseudonymisation in the re-identification sense: FIR numbers, police stations, dates and places pass, and the `pseudonymised` mode needs no per-case consent although four documents say it does.
5. Fix the three measurement problems and the report text first (all are small); then prune the claim set to what the budget can test; the harness itself is worth keeping as the contribution.

## Strongest decisions

- **Ablations as typed switches with byte-identical defaults** (`orchestration/switches.py:189-225`, golden default-run tests, `assert_variant_implemented`). It turns every literature idea into a controlled one-factor change and makes "Full did not change" testable. This is the best single decision in the project.
- **Code stamp in every manifest and a scorer that refuses mixed commits** (`sweep-dev.md`, `eval/scoring/loader.py`). It caught the `719f741-dirty` runs and the v1/v2 split; most course projects would have scored them.
- **Spend ledgers that reserve the worst case before the request** (`models/openai/ledger.py`, `models/sarvam/spend.py`, `BEGIN IMMEDIATE` across processes). Parallel shards cannot overshoot; this made hosted runs safe to delegate.
- **Approval read only from the event log, never from a resume value** (`orchestration/gates.py:1-8`, `record/gates.py:81-142`); Gate 2 requires Gate 1, and export checks the latest gate event for that very case (no bulk export).
- **Span-grounded labeler that is not shown the rule candidates** (`gold-labeler.md` Task B). Removing the confirm-the-candidates design avoids measuring acquiescence; the verbatim-span rule is a cheap, deterministic validity check.
- **Null-agent audit and the M6 fix for briefs with no claims** (evaluation-plan 5.7; `case_metrics.answerable_coverage`). The team found and fixed a metric that rewarded silence.
- **Honest negative notes.** `dev-baselines.md` failure mode 2 (Full may win on retrieved boilerplate when facts are only a caption) and the report's Limitations are the kind of self-criticism reviewers reward.
- **Unsettled law returns CHECK, never ELIGIBLE** (`rights-fixes.md`, `configs/rights_rules.yaml`); the false-ELIGIBLE rate is the right safety number for F3.
- **Frontend rules with explicit "do not" lists and input parity** (`frontend/DESIGN.md` "Things we do not do"; branch "Parity: every drag has a button and a keyboard path"). The branch keeps scroll native and confines physics to things under the hand.

## Weak or risky decisions (ranked)

### 1. The unsupported-fact rate (M6) is measured with the system's own checker
- Evidence: `eval/metrics/unsupported_fact.py:19-45` uses MiniCheck only if the `minicheck` package is importable, else `models.factory.get_nli()`; in `.venv` `find_spec('minicheck')` is None, so M6 uses DeBERTa-v3 NLI. Vakeel's check-and-repair also calls `get_nli` (`agents/vakeel/agent.py`, `agents/base.py`). The owner's and Satvik's runs are explicitly scored "with the real DeBERTa claim checker" (`sweep-dev.md`, `sweep-satvik.md` step 2). The evaluation plan's validity argument (`evaluation-plan.md` 2.4, row "Unsupported-fact rate": "the system's own repair uses a different checker (DeBERTa NLI), so the metric is not circular") and `skeleton.md` ("MiniCheck ... never by the system") therefore do not hold. Also, the code loads `MiniCheck(model_name="flan-t5-large")` while the weights on disk are `lytang--MiniCheck-RoBERTa-Large`.
- Why it matters: Full repairs claims until DeBERTa accepts them; B0 and B1 never repair. Even with a different premise (input facts vs cited paragraph) the shared model's blind spots favour Full on C2, the second headline claim.
- Fix: install MiniCheck (`.[eval]`), point it at the RoBERTa-Large checkpoint on disk, make `unsupported_fact_rate` refuse (not fall back) when the evaluation checker equals the system checker, and record `checker` in every table. Report the deterministic verbatim-span check beside it. Effort: S.

### 2. The gold labeler and the evaluated system are the same model
- Evidence: G1, G3 to G7 are agreed between rules and `gpt-6-luna` (`gold-labeler.md`, `evaluation-plan.md` 5.9 "Gold-source sensitivity"); Full, B0, B1, B4, B6 dev runs are on `gpt-6-luna` (`dev-baselines.md`, `sweep_dev.yaml` phase 0 and 2). The "non-Qwen labeler" rule (`AGENTS.md` hard rules; `skeleton.md` conventions) was written when the system was Qwen; it now gives no independence. The finetune option (a) uses `gpt-6-luna` as teacher (`finetune.md`), which would also break the "teacher and labeler are different families" rule (`skeleton.md`, `evaluation-plan.md` 2.6).
- Why it matters: the labeler's reading of "weak prima facie" (101 labeler-only labels, `gold-labeler.md`) and the drafter's reading of the same idea come from one model, so recall against agreed gold is biased toward systems that use that model, and the agreed gold is the primary gold. Between Full and B0 on the same model the bias is shared, but a reviewer will ask why the labeler is not independent of the judged system, and it matters for any cross-backend comparison (Sarvam block, B0L).
- Fix: state it as a threat in the report; report rule-only gold as a co-primary for the main table (it is already computed, `--gold-source both`); for the Sarvam block, use the existing Sarvam-105B G1 labels (kappa 0.784 with gpt-6-luna on 80 orders) only as a sensitivity column, not as gold; never use `gpt-6-luna` as teacher. Effort: S.

### 3. The dense retriever is a hashed n-gram embedder, and the report says BGE-M3
- Evidence: `data/stores/MANIFEST.json` `"embedder": "hashed-ngram"`; `data-and-models.md` (build command `EMBEDDER=hashed-ngram`); `stores/hybrid.py:128-142` reuses the embedder recorded in the index. The report says "reasoning paragraphs (BM25 plus BGE-M3, metadata pre-filter)" (`report/sections/system.tex`), plan 15.3 defines B2 with BGE-M3, and `sweep-dev.md` speaks of "real BGE-M3 retrieval".
- Why it matters: "hybrid" retrieval is two lexical signals; B2 (whole-document embeddings) and B3 (chunking) test granularity with an embedder that has no semantics, so their results say little about the plan's question; any retrieval claim (C5, C14, S16) is about a weaker retriever than described.
- Fix: either rebuild the reasoning and similar stores with BGE-M3 on Ada or the laptop (the full build took about 35 minutes with the hashed embedder; BGE-M3 on 160K paragraphs needs a GPU), or correct every document to "BM25 plus a hashed n-gram vector" and drop B2/B3 granularity claims. Effort: S (text) or M (rebuild).

### 4. Full against B0 is confounded by compute, and "argued" is counted generously
- Evidence: measured tokens per case: Full about 94,000, B4 about 119,000, B1 about 7,200, B0 about 3,800 (`dev-baselines.md` cost table). The scorer counts every ground that is not the placeholder and whose stance is favourable or adverse as an argued factor (`eval/scoring/case_metrics.py:10-12`), so adverse grounds and `NEEDS_REVIEW` grounds score recall; Full's first outputs had 91 REPAIRED, 72 SUPPORTED and 58 NEEDS_REVIEW grounds (`dev-baselines.md`). The answerable-factor rule uses the rule method only (`case_metrics.answerable_of`), not "the same two methods" agreed (plan 15.1). T1 `facts_text` is often only a caption (`pilot-hosted-model.md` quality notes).
- Why it matters: C1 "Full finds more argued factors than B0" can be won by a system that spends 25 times the tokens, retrieves boilerplate, and emits grounds it marks for review. Only S9 controls compute, and only for sparring.
- Fix: (a) add an equal-token single-model baseline (B0 with k samples and a union or vote, the S9 idea applied to drafting; `draft_mode='vote'` already exists as S11c); (b) report recall twice, counting all grounds and counting only SUPPORTED or REPAIRED favourable grounds; (c) restrict the headline to cases with at least one answerable factor by the agreed method, and print n; (d) keep `answerable_coverage` in Table 1. Effort: S to M.

### 5. The pseudonymisation boundary misses quasi-identifiers, and consent is not required for pseudonymised text
- Evidence: `privacy/pseudonymise.py:1-6` is rule-based (names after role words, emails, phones, ID numbers; Presidio and InLegalNER "plug in later"). There is no rule for FIR numbers, police stations, villages, addresses or dates; the pilot's hosted output contained "FIR 87/2023, Hili police station, NDPS sections 21(c), 22(c), 23(c), 27A" (`pilot-hosted-model.md`). The residual-leak proxy found party-name tokens in 5 of 250 orders after the fix while the boundary refused only 1 (`pilot-hosted-model.md`, "Pseudonymiser: caption names"), so at least 4 orders with leaked name tokens passed. `models/sarvam/policy.py:217-280` requires counsel's consent only for `CLIENT_RAW` (mode `consented`); `CLIENT_TEXT` under `pseudonymised` needs no consent. AGENTS.md, plan §16, the report (`system.tex`, "and per-case consent") and product-readiness AC-P ("A Sarvam mode above `public` needs a per-case consent event") say otherwise.
- Why it matters: an FIR number plus police station identifies a case on public portals, so "pseudonymised" client text is re-identifiable; C38 ("names planted in client files never reach external payloads; falsified by any leak") is already falsified by the team's own proxy on public data. For a legal-aid client this is the main real-world harm the product could cause.
- Fix: decide the policy in writing (recommended: per-case consent for any client text, pseudonymised or not); add FIR-number, police-station, village and exact-date generalisation (dates to relative day offsets, which the Rights Radar already computes locally); make the boundary refuse when the leak proxy fires, not only when its own rules fire; state in the report that the boundary is a name scrubber and give the residual-leak rate with its denominator. Effort: M.

### 6. The test-scale evaluation has no backend, and the report is anchored on superseded runs
- Evidence: `configs/eval/runs.yaml` `rq1_full` "target 2400 case-runs (14 USD on gpt-6-luna): over the OpenAI cap, so it runs on Ada (Qwen)"; the Qwen path on Ada never served (`ada-qwen32b.md`), no 14B is set up, and the fine-tuned 4B does not exist (`finetune.md`). On disk every dev run has `git_sha efd0ce4` (v1); no run exists on `dev-sweep-v2` (progress 0f; checked in `data/eval/dev_runs/outputs/*/MANIFEST.json`). Yet `report/sections/results.tex` ("What ran ... rerun ... from a clean worktree of the tag `dev-sweep-v1`") and the status table ("Score dev reruns at tag `dev-sweep-v1`: to do") plan to score v1, which `sweep-dev.md` (06:35 update) says must not be scored with v2.
- Why it matters: every "supported" claim requires the blind slice (`evaluation-plan.md` 1.1), and nothing can reach the blind slice under the current budget and backends. The status report will be dev-only by construction; the plan still reads as if a test run follows.
- Fix: decide now which backend runs T1 test at the floor (for example Full and B0, B1, B4 on 120 open + 80 blind on `gpt-6-luna` is about 200 x (0.0077 + 0.0005 + 0.0009 + 0.0084) = about 3.5 USD per run on a fresh ledger, so one run fits a teammate's 5 USD key); rewrite `results.tex` to the v2 tag or explicitly report v1 as superseded; add a "what can and cannot be claimed from dev" paragraph. Effort: S (text), M (run).

### 7. Rights Radar: unverified status is invisible, T4 is no longer independent, and F3 is close to a tautology
- Evidence: `frontend/components/workspace/tabs/RightsTab.tsx:144-149` shows "Rule checked" only when `last_verified` is set; an unverified rule shows nothing, and no frontend file renders the API's `verification` field (searched `frontend/components`, `frontend/lib`, both branches). `rights-fixes.md` shows one change editing `rights/rules/*.py` and `testsets/rights_spec_writer.py` together, while plan 15.2 and evaluation-plan 2.4 require T4 to be written "by a team member who does not write the Radar code". T4 answers are derived from the same rule table the Radar implements (`testsets-t2-t9.md`: "a consistency check, not a legal one"), so C30 ("Radar more accurate than the LLM on T4") compares the LLM against the Radar's own specification. `grounds_of_arrest` behaviour changed but kept its `last_verified` because "the rule text is unchanged" (`rights-fixes.md`); `production_24h` is dated verified while the store text of BNSS s.58 is the body of s.59 (`rights-fixes.md`, person task 1).
- Fix: show "Not yet checked against the bare act" in the UI and the DOCX for every rule with `verification: unverified` (a negative label, not the absence of a positive one); bind `last_verified` to a hash of rule text plus rule code so a behaviour change clears it; report C30 as "agreement with the written rule table" and drop the comparative framing, or have Harshita write the new 127 scenarios by hand from the acts (no LLM); mark `production_24h` unverified until s.58 text is fixed. Effort: S.

### 8. Breadth over depth in the evaluation design
- Evidence: 61 variant ids pass the offline audit (progress 0f); 42 claims (`evaluation-plan.md` 1.2); 9 Holm families; sweep phase 1 runs most arms on the offline stand-in, where "offline S8 never repairs by itself; offline S10 ignores what it reads" (`literature-sweep-2.md`) and "attack-success numbers describe the stand-in, not a model" (`sweep_dev.yaml` S17). The Tier A floor was 229 node-hours against about 180 usable (`evaluation-plan.md` 7.4), and the Ada path is gone. At n = 50 the plan's own resolution is about 7 points (5.4), larger than δ.
- Why it matters: a reviewer will read 18 variants with no real-model result as plumbing, and the number of untested claims will dominate the report. Stand-in results invite misreading.
- Fix: for the report, keep a small primary set: C1/C3 (with the compute-matched baseline), C2 (with an independent checker), C4, C13 (S8), C7 (S9), C10 (A6, A7), C36 to C38 (safety, deterministic). Move everything else to an appendix table "built, not measured", and do not print offline-stand-in numbers in the body. Effort: S.

### 9. The evaluated system is narrower than the six-agent claim, and some defaults name things that do not exist

B4 differs from Full in more than "an agent choosing" once Full's budget pools and sufficiency rules are counted; S12b (`topology='single_agent'`) is the cleanest test of whether the multi-agent split earns its tokens and is only a "should".
- Fix: in the report, say which agents each result covers; record the effective model per role in the manifest (`describe_run_models()` already exists) and print it in Table 1; promote S12b to a primary comparison beside B4; rename the default extractor to the role actually used, or make the switch fail when the adapter is missing. Effort: S.

### 10. Gate 2 approval is not bound to the content it approved, and "counsel" is a string
- Evidence: `record/gates.py:81-120` stores a `dossier_hash` with Gate 1 but nothing for Gate 2; `assert_export_allowed` (`record/gates.py:122-142`) checks only that the latest Gate 2 event is an approval. Revocation depends on every mutation path calling `request_approval` (only `agents/vakeel/agent.py:1549` does). `api/auth.py:3`: "Without `VS_API_TOKEN` the API trusts every caller as counsel"; the token is off by default and the UI does not send one (`frontend-endeavours.md`, Known issues).
- Fix: store a brief hash (grounds, sparring record, List of Dates) with the Gate 2 approval and refuse export when the current hash differs; make `VS_API_TOKEN` default on in the Docker profile with a generated token shown once; keep the report's honest "property of the code path, not of an identity check". Effort: S.

### 11. Statistics: families, pairing and leakage details
- Evidence and issues:
  - C1 is "supported only if it holds against all five" baselines (`evaluation-plan.md` C1). That is an intersection-union test, which is valid at α per comparison without Holm; applying Holm across the six makes C1 harder to support than the claim requires. Holm is the right tool for "against which baselines does Full win", not for "against all".
  - `eval/scoring/engine.py:63-70` families differ from plan 5.3: `F-sparring` omits `s8` (C13), and `F-ablate-recall` tests C11 and C12 on factor recall although their metrics are the unsupported-fact rate and tool accuracy (plan C11, C12). Missing comparators count as p = 1 (conservative, good), so B0L, B2, B3 that will not run shrink power for nothing.
  - The sparring family spans backends: A2, A8, A9 run on OpenAI (phase 2) and S8, S9, S10 on Sarvam (phase 3) (`sweep_dev.yaml`). Each block has its own Full, so the comparisons are paired, but one Holm family mixes two models.
  - M6 is undefined for briefs with no claims; a paired bootstrap that drops pairs with a missing value compares Full and B0 only on the cases where B0 chose to write something, a selection effect. Report the paired count and the abstention-aware `answerable_coverage` with it.
  - Gold diagnostics (per-factor kappa) were computed on 250 orders that include the 80 blind orders (`gold-labeler.md`), and the G2 merge changed 14 test cases after the blind ids were hashed (`dev-baselines.md`). The ids hash is unchanged, but the gold content of the blind slice is not sealed, and any later gold-rule change informed by these kappas is tuning on test.
- Fix: register C1 as an intersection-union claim; align `FAMILIES` with plan 5.3 or amend 5.3; register one family per backend; hash the blind gold rows (not only ids) into the pre-registration; compute future label diagnostics on dev only. Effort: S.

### 12. Frontend: the physics amendment is sound but needs a rule change and one safety fix
- Evidence: AGENTS.md hard rule "short motion only (150 to 300 ms)"; main DESIGN.md already has `--dur-fast` 120 ms, 1.2 s loops and an 8.55 s hero loop; the branch adds gesture springs that settle within 450 ms (`git show frontend-endeavours:frontend/DESIGN.md`, "Direct manipulation and springs"). The branch separates time-based motion (150 to 300 ms) from motion under the hand, which is the right distinction, but AGENTS.md has not been amended. The gate "hold" (12 px give, lists open items) is a good pattern for a blocked gate; it must not become hold-to-approve. The landing grew from 122 kB to 183 kB first load (`frontend-endeavours.md`).
- Fix: amend the AGENTS.md rule to "time-based motion 150 to 300 ms; gesture-driven springs settle within 450 ms; loops only for running work"; before merge, add the Rights `verification` label (item 7) and the `VS_API_TOKEN` header (item 10) so the branch does not ship the older API contract. Effort: S.

## Report-claim risks

What a reviewer of the ACL-format status report would attack, in order:

1. **"Every claim is checked" and the unsupported-fact rate.** The checker that scores M6 is the checker that repaired Full's claims (item 1). Until MiniCheck runs, do not print M6 as a comparison; print the verbatim-span check.
2. **"A non-Qwen model labeler" (abstract, `evaluation.tex`).** True but beside the point: the labeler is the system's own model. Say so in the abstract-level text, not only in threats.
3. **"Seven simpler baselines".** B0L is dropped, B2 and B3 have not run (`results.tex` todo), B5 is a learned router, not simpler, and B6 is scored on precision only. Count what ran.
4. **"18 single-switch variants ... each adapted from a paper checked on its official page".** P8 has no paper (`literature-to-code-map.md` row P8); S13, S14b, S14c, S16, S16b are studies, not per-case arms (progress 0f); none has a real-model result. Say "built" and "measured" separately.
5. **"BM25 plus BGE-M3".** Wrong for the measured stores (item 3).
6. **"Raw client files stay on the user's machine ... pseudonymisation boundary".** True for files; the payload still carries FIR numbers, police stations and dates; the ethics statement's "5 of 250 after the fix" omits that 4 of those 5 passed the boundary (item 5).
7. **"Two approval gates ... approvals can only come from counsel".** Counsel is an actor string and the API trusts every caller without `VS_API_TOKEN` (item 10); the Limitations already say so, so keep that wording in the contributions list too.
8. **Dev-only, one backend, v1 runs.** `results.tex` describes v1 runs that progress 0f calls superseded; no paid run exists on v2. Any number in the abstract (`\todo` factor recall, M6, USD per case) would be from superseded code unless v2 runs first.
9. **Thin facts.** The report's own Limitations admit Full can win on retrieved boilerplate. Without the stricter recall (SUPPORTED or REPAIRED favourable grounds only) and a compute-matched baseline, a C1 result invites the reading "more tokens, more factors".
10. **Rights Radar accuracy.** T4 is generated from the rule table the Radar implements, by the same change; present F3 as conformance, not accuracy, and show "unverified" in every Rights output.
11. **Statistics language.** With n = 50 the half-width is about 7 points (plan 5.4), above δ = 5; say "not resolved" rather than "no difference", and say that no claim can be "supported" without the blind slice.
12. **Store sizes and coverage.** Report the 14 of 200 test orders with a resolved citation next to any G2 number, and that dev has 0 (already in `evaluation.tex`; keep it next to every G2 table, not only in the text).
