Find the architecture (pipeline, paradigm, number of agents) that beats **every baseline (B0 to B6) on every metric**, then run the ablations on it, then ship it as the product backend and frontend. Until a configuration does that on the dev search cases, the search keeps iterating.

- New behaviour is an opt-in switch in `src/vakeel_sahayak/orchestration/switches.py` (defaults byte-identical, paper citation, row in `docs/literature-to-code-map.md`); tests are never weakened.
- No change to gold labels, the scorer or a metric definition to win. The case-fact split metric (M6a) is reported **beside** the original unsupported-fact rate, for every arm, never instead of it.
- Search on dev cases `t1dev-000..029`, confirm once on `030..049`, blind slice once (5 to 7 Nov). Sarvam-105B only (cap INR 5000 in total, about INR 240 spent; the search has INR 900), OpenAI locked, payloads pseudonymised.
- A win is counted only when the paired interval excludes zero. Ties are reported as ties.

Dates: architecture chosen by 4 Nov; backend and frontend for it by 6 Nov; open and blind runs 5 to 7 Nov; scoring 7 to 9 Nov; freeze and submit 10 Nov.

## Satvik: metrics, statistics, Rights (all scripted, no manual work)

- Win/loss/tie table: a script that reads the scorer output and, for every arm against every baseline on every metric, gives the paired bootstrap interval with Holm correction; a win only when the interval excludes zero.
